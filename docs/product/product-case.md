# AI 日程助手：产品案例与用户研究 Demo

## 1. 问题定义

目标用户是需要同时处理工作、社交、运动和办事安排的年轻移动端用户。产品假设是：他们缺少的不是“再一个日历”，而是从日程信息到准备行动之间的转换。

当前问题判断来自场景分析和产品假设，尚未完成正式用户访谈，因此本文不把假设写成已验证结论。

## 2. 核心用户任务

> 当我安排一次面试、聚餐、运动或办事时，我希望快速得到可信的准备清单、时间建议和风险提醒，以便降低遗漏和临时决策成本。

## 3. 需求拆解

| 阶段 | 用户问题 | 产品响应 | 验收信号 |
| --- | --- | --- | --- |
| 输入 | 描述很口语，不想填很多字段 | 自然语言解析，同时保留手动入口 | 用户能在一次确认内完成创建 |
| 确认 | AI 是否理解错了时间或地点 | 保存前展示结构化字段 | 关键字段可见、可修改 |
| 准备 | 我具体该做什么 | 输出时间线、清单、风险和建议 | 建议可以直接执行或勾选 |
| 执行 | 什么时候准备和出发 | 结合时间、地点和提醒风格 | 提醒节点与日程一致 |
| 回看 | 日程和建议放在哪里 | 今日、日历和详情页联动 | 创建后可以从日历重新进入 |

## 4. v0.1.0 优先级

### Must

- AI 与手动两种创建方式。
- 用户确认后再保存。
- 结构化行动方案。
- 今日、日历、详情与偏好页面闭环。
- 网络/模型失败时可继续手动创建。

### Should

- 路线、天气和本地通知上下文。
- 不同日程类别的差异化建议。
- AI 建议风格和提醒风格偏好。

### Not now

- 账号、云同步和多人协作。
- 系统日历双向同步。
- 语音和图片输入。
- 自动代替用户执行操作。

## 5. 关键产品决策

### 为什么不做纯聊天界面

聊天适合表达需求，但不适合回看和执行。输入阶段可以对话，输出阶段必须回到时间线、清单和风险卡片。

### 为什么 AI 不能自动保存

时间与地点错误会直接影响提醒和出行。将“确认”设计成硬门槛，可以把模型能力放在提效位置，而不是让用户承担不可控副作用。

### 为什么保留手动入口

AI 是增强层，不应成为基础功能的单点故障。即使网络、模型或配额不可用，用户仍能创建日程。

## 6. 用户研究 Demo

这是后续真实访谈可直接使用的研究方案，而不是伪造的访谈结果。

### 招募建议

- 5 名每周至少创建 3 次日程的用户。
- 覆盖职场新人、学生和自由职业者。
- 至少 2 名经常需要跨地点出行的用户。

### 访谈任务

请用户用自己习惯的方式创建“明天下午三点去某地面试”的安排，并完成以下任务：

1. 说出你通常会在哪些地方记录这件事。
2. 展示你会提前准备哪些内容。
3. 使用 AI 创建并检查结构化结果。
4. 判断哪些建议有用、泛化或令人不信任。
5. 找到第二天的日程并修改提醒偏好。

### 观察点

- 是否理解 AI 不会在确认前保存。
- 是否能发现时间、地点或类别解析错误。
- 首次有效方案需要几次操作。
- 哪类建议最先被执行或忽略。
- 用户是否愿意开放位置与通知权限。

## 7. 建议指标

这些是下一阶段应采集的指标，目前没有真实线上数据：

| 指标 | 目的 |
| --- | --- |
| 创建完成率 | 判断输入与确认流程是否顺畅 |
| 首次结构化结果接受率 | 判断解析质量是否达到可用门槛 |
| 平均字段修改数 | 定位时间、地点和类别的主要错误 |
| 建议清单完成率 | 验证 AI 输出是否真正可执行 |
| 次日回访率 | 验证产品是否形成持续使用价值 |
| 通知/定位授权率 | 判断上下文能力与隐私成本的平衡 |

## 8. 下一步验证

先完成 5 人可用性测试，重点验证“确认门槛”和“建议可执行性”。如果用户能够快速完成创建，但很少执行建议，应优先改进建议质量，而不是继续增加账号、社交或复杂日历功能。
